### [#183](https://github.com/ocapn/ocapn/issues/183) Perimeter Types

Jessica: The perimeter types issue is an issue I filed quite awhile ago. Goblins uses a bunch of types that are not defined in OCapN, such as vectors and dotted-lists and keywords.  Goblins wants to support those because they are common types in Scheme but are somewhat esoteric. I don't want to propose them as types in OCapN and I don't think there would be support for it. That's why we are proposing these extension types. We currently use the tagged type to wrap user or system tagged values. That isn't our proposal.

MarkM: Can I ask a question in realtime?

MarkM: Is this proposed as an alternative to tag or a replacement to it?

MarkM: This sounds plausible to me.

Jessica: This proposal has two parts to it. The proposal is to use the tagged type to express language-specific types, which have today. In the issue I have shown defining two tagged types for dates that use different formats. This shows an issue that we have a solution for: content-addressed descriptors. You can have a description of the type and hash it so its unique.

MarkM: Is that a human readable or machine readable description?

Jessica: Machine readable. And we are not proposing that OCapN adopt this specifically. You could also use linked data. But the point is that it avoids collisions. However, having the type name be a hash makes the type names really long and thus take up a lot of space in messages. This proposal includes a symbol table so each peer can expose some symbols of their choosing that get mapped to integers and then the peer can refer to the symbol with a small integer. So for example you could map <some-long-symbol> to an integer. We propose a limited number of symbols to avoid attacks where a malicious peer fills up the remote side's memory by registering lots of long symbols. It's an optimization, though it's a required optimization so a peer can understand what another peer is saying if that remote peer is using registered symbols. So that's the proposal: Have a way to register symbols and then use content-addressed descriptors, or linked data, or something else. Then you could have a tagged error and it would be well-understood to be a JS error and not some other kind of error.
